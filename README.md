# Шаркающий человек | Shuffling Man

Жанр: Визуальная новелла / психологический хоррор.
Сеттинг: Москва, начало 2000-х

## О проекте

"Шаркающий человек" — история о распаде семьи, психическом расстройстве и границе между реальностью и галлюцинацией, рассказанная через призму ненадежного рассказчика.

### Ключевые особенности

Ненадежный рассказчик: История подается через записи Марины, но её восприятие реальности искажено психическим состоянием.

Двойственность повествования: Игрок видит "идеализированную" версию событий глазами Марины (чистая палата, ухоженные волосы, приветливый врач), которая постепенно разрушается, открывая мрачную реальность (побритая голова, камера для душевнобольных, металлический стол).

Атмосфера бытового ужаса: Хоррор строится на нарастающем психологическом давлении — от мелких семейных раздражителей до экзистенциального кошмара.

Визуальный стиль: Реалистичные бэкграунды российской хрущевки 2000-х годов с нарастающим визуальным искажением, отражающим психическое состояние героини.

## Для разработчика

### Технологический стек:

- renpy-8.5.3-sdk – движок игры
- ./game/libs/7dots.rpy – библиотека 7dots с базовыми функциями-расширениями. **Обязательна к использованию**: перед реализацией любой функциональности (аудио, трансформации, анимации, переходы, эффекты, UI, управление диалогом) сначала проверить, есть ли готовое решение в 7dots, и использовать его, не дублируя. Справочник — skill `7dots-reference` (см. AGENTS.md)

### Конвенции

Основано на документации Ren'Py 8.5.3 (`../renpy-8.5.3-sdk/doc/`). Python внутри движка — 3.12.

#### Структура файлов

Текущая структура `game/`:

```
game/
├── 0_prologue/      — сцены пролога
├── 1_chapter/       — сцены главы 1
├── 2_chapter/       — сцены главы 2
├── 3_chapter/       — сцены главы 3
├── 4_endings/       — концовки и эпилоги
├── common/          — переиспользуемый код: шейдеры, трансформы, утилиты
├── audio/           — music/, sfx/, voice/
├── images/          — 0_prologue/ … 4_endings/, common/
├── gui/             — графика интерфейса
├── fonts/           — шрифты
├── libs/            — библиотеки (7dots), libs.txt задаёт порядок загрузки
├── tl/              — переводы
├── dev/             — dev-инструменты, из дистрибутива вырезаны (build.classify)
├── fx_config.yaml   — сквозные параметры визуальных эффектов
├── script.rpy       — точка входа; прыгает на титры пролога
├── options.rpy, gui.rpy, screens.rpy
```

- Весь код игры — в `game/`, файлы `.rpy`. Код допустимо делить на файлы, но аккуратно и осмысленно — избыточное дробление создаёт путаницу. Служебный код — `characters.rpy`, `images.rpy` (при необходимости), `libs/` — библиотеки.
- **Переиспользуемый код — в `game/common/`**: всё, что используется (или очевидно будет использоваться) более чем одной сценой/главой — шейдеры, трансформы, экраны, функции-утилиты. Файлы — тематические: `common/shaders.rpy`, `common/transforms.rpy`, `common/screens.rpy` и т.п. В папках глав остаётся только код конкретных сцен; заметил, что кусок кода нужен второй сцене — сразу выноси в `common/` (сцены задают специфику параметрами, а не копиями кода). Сторонние/крупные библиотеки — по-прежнему `libs/`.
- Сценарные `.rpy` внутри папок глав допустимы максимум на одном уровне вложенности. Технические деревья `images/`, `audio/`, `dev/`, `gui/`, `libs/` и `tl/` могут иметь нужную им вложенность.
- Папки этапов повествования имеют числовой префикс для сортировки в дереве проекта: `0_prologue/`, `1_chapter/`, `2_chapter/`, `3_chapter/`, `4_endings/`. Номер главы живёт в префиксе и не дублируется в имени папки. Количество частей фиксировано сценарием, запас в нумерации не оставляем. Префикс `00` не использовать (зарезервирован движком); префикс влияет только на отображение — порядок загрузки управляется `libs/libs.txt`. Имена файлов префиксов не получают.
- Имена файлов и папок — строго на английском языке, в нижнем регистре. В `.rpy`-файлах, папках и аудио слова разделяются `_`; исключение — файлы изображений, где имя строится по формату «тег атрибут» через пробел (см. «Изображения»).
- Имена файлов — избыточные: имя полностью дублирует структуру повествования, даже внутри папки главы. Файл должен однозначно идентифицироваться по одному имени, без учёта пути.
  - Сцены: `prologue_scene_1.rpy`, `chapter_1_scene_1.rpy`, `chapter_1_scene_3.rpy` (в папках `0_prologue/`, `1_chapter/` и т.д.).
  - Концовки: отдельная папка `4_endings/`, файлы `ending_1.rpy`, `ending_2.rpy`.
  - Мини-игры: в папке своей главы, имя дублирует структуру вплоть до сцены: `2_chapter/chapter_2_scene_3_minigame_piano_1.rpy`.
- Имена файлов не начинаются с `00` (зарезервировано движком) и начинаются с буквы или цифры.
- При удалении/переименовании `.rpy` обязательно удалять осиротевший `.rpyc`, иначе старый код продолжит исполняться. `*.rpyc`, `game/cache/`, `game/saves/` — в `.gitignore`.
- Отступы — только пробелы (4), единообразно во всём блоке.

#### Dev-инструменты (F6, F9, F10, F12)

Работают только в dev-запуске (`config.developer`); `game/dev/**` в дистрибутив не попадает.

##### Dev Hub — F12

`game/dev/dev_hub/`: единая точка входа — инструменты проекта и встроенные инструменты Ren'Py с горячими клавишами из текущего `config.keymap`, строка статуса (файл:строка, лейбл, ключевые переменные, несохранённые правки FX Tuner). Новый инструмент проекта добавляется записью в `DEV_HUB_TOOLS`.

##### FX Tuner — F10

`game/dev/fx_tuner/`: параметры визуальных эффектов вживую, поверх идущей игры. Значения живут в `game/fx_config.yaml`: файл читается при запуске, в том числе в релизе; сейвы и rollback его не хранят. Ручную правку файла во время игры подхватывает «Перечитать файл»: autoreload на этот файл не реагирует, чтобы сохранение из панели не перезапускало игру.

- `F5` — сохранить в YAML; «Откатить к файлу» и «Перечитать файл» возвращают значения с диска. Остальные клавиши — в подсказке панели.
- `B` — A/B: эффекты временно выключены; `P` — превью: переменная сцены игнорируется, эффект виден в полную силу.
- Панель на слое `top` и не modal: эффект с охватом «весь экран» её не задевает; клики мимо панели и клавиши, не занятые ею (стрелки, `R`, `B`, `P`, `F5`, `Esc`), идут в игру; `Esc` закрывает.
- Position Tuner и Path Tuner живут на слое `screens` и при охвате `screen` постеризуются вместе с UI; на время подбора включите A/B.

##### Path Tuner — F6

`game/dev/path_tuner/`: графический редактор spline-траекторий поверх идущей игры. Кликами ставятся опорные точки, крайние ручки задают касательные, призрак спрайта проигрывает движение; `Ctrl+C` кладёт в буфер готовый ATL с `knot` (Безье при двух точках, Catmull-Rom при трёх и больше), режим «по касательной» доворачивает спрайт по ходу кривой. Документация — [game/dev/path_tuner/README.ru.md](game/dev/path_tuner/README.ru.md).

##### Position Tuner — F9

Числа размещения в сценах пишутся прямо в `show ... at`/ATL, без `define`-констант (константа — только если значение читает другой файл: мини-игра, тест, `common/`). Подобрать числа помогает dev-инструмент **Position Tuner** — `F9` в любой сцене (`game/dev/position_tuner/`, в дистрибутив не попадает).

- Обводит по контуру все спрайты на экране и показывает точные параметры выбранного: позицию, точку привязки, **угол наклона**, зум, собственный размер картинки и её габариты на экране. Значения читаются из живых трансформов сцены.
- Выбранный спрайт можно потащить мышью или стрелками, сменить точку привязки (`Tab`) и угол (`[` и `]`) — призрак показывает результат, панель считает новые числа. `Ctrl+Z` отменяет, `R` возвращает значения сцены.
- `Ctrl+C` кладёт в буфер готовый блок ATL или вызов `placed(...)` — вставляете в код руками.
- Инструмент ничего не записывает и сцену не меняет. Документация — [game/dev/position_tuner/README.ru.md](game/dev/position_tuner/README.ru.md).
- Подгонять удобнее в песочнице `dev_position_sandbox` (`game/dev/dev_utils.rpy`): сцена без камеры и параллакса, где призрак совпадает со спрайтом пиксель в пиксель.

#### Комментарии и docstring

- Комментарий объясняет **почему** код устроен так, фиксирует ограничение или предупреждает о неочевидном последствии. Он не пересказывает следующую строку и не дублирует имя переменной или функции.
- В сценариях оставлять краткие ориентиры по последовательности сцен, фазам эпизода, развилкам, условиям выбора и их последствиям.
- В коде комментировать только сложные инварианты: порядок слоёв и событий, save/rollback, ввод и click-through, систему координат, синхронизацию, совместимость и ограничения Ren'Py.
- Заголовки нужны только у крупных логических блоков. Декоративные разделители, пошаговые учебные пояснения, очевидные подписи, закомментированный старый код и примеры «на всякий случай» не оставлять.
- Docstring подчиняется тем же правилам: только краткий контракт сложной функции или класса, обычно одна строка. Тривиальным и приватным helper-функциям docstring не нужен.
- Inline-комментарий использовать только для короткой единицы измерения или локального ограничения, которое нельзя ясно выразить именем. Сложное объяснение ставить отдельной строкой перед кодом.
- `TODO` должен быть коротким и проверяемым: `TODO(звук): щелчок метронома.` Без «потом», «при необходимости» и других формулировок без действия.
- При изменении поведения одновременно обновлять или удалять устаревший комментарий. Лицензии, vendored-warning и сгенерированные source-map комментарии Ren'Py (`game/tl/**`) сохранять; файлы переводов вручную ради чистки комментариев не редактировать.

#### Переменные: define / default / $

- `define` — только для констант (персонажи, transitions, transforms, пути): не сохраняется, менять после init нельзя.
- `default` — для ЛЮБОЙ переменной, меняющейся по ходу игры (флаги, счётчики). Никогда не инициализировать игровые флаги через `$` в start или `init python` — сломаются сейвы и новые игры.
- `$` — одиночные строки Python по ходу сценария; `python:` — для блоков; `init python:` — функции/классы. Временные переменные — в `python hide:`.
- Не переиспользовать одно имя под персонажа и флаг. Имена с `_` в начале зарезервированы движком; исключение — внутренние помощники модулей с уникальным префиксом (`_fx_`, `_fxc_`, `_pt_`), которые не являются игровыми переменными. Приоритеты init — в диапазоне −999…999, у обычного кода 0+.
- Файлы, генераторы, лямбды, корутины не пикнутся в сейв — не хранить их в переменных store (только внутри `python hide` или функций).

#### Персонажи

- Все персонажи — через `define` в одном файле, короткие имена: `define m = Character("Марина", color="#...")`.
- Реплики без рассказчика — просто строкой (narration). Шаблонные вариации персонажа — через `kind=`.
- Имя героини в галлюцинациях/искажениях можно менять через `dynamic=`.

#### Изображения

- Основной способ определения — папка `game/images/`: имя файла в нижнем регистре = имя образа. Формат имени: `тег атрибут атрибут`, напр. `marina room sad.png` → `show marina sad`.
- Пробел разделяет только тег и атрибуты. Многословные имена внутри тега или атрибута пишутся слитно через `_`: `prologue dark_room.jpg` (тег `prologue`, атрибут `dark_room`), `prologue_hand_right write.png` (тег `prologue_hand_right`, атрибут `write`).
- Полноэкранные изображения одной сцены/части носят общий тег этой части (напр. `prologue`) и различаются атрибутом-именем: `prologue dark_room.jpg`, `prologue head.jpg`, `prologue pencil_close.jpg`. Показ нового кадра с тем же тегом автоматически заменяет предыдущий.
- Анимируемые объекты: тег соответствует объекту и уникален во всём проекте (не перекликается с другими тегами), его анимации и переходы — различающиеся атрибуты: `prologue_hand_right.png` (базовый кадр), `prologue_hand_right move.png`, `prologue_hand_right write.png`.
- Подпапки **обязательны**: по главам (`0_prologue/`, `1_chapter/`, …, `4_endings/`), внутри при необходимости — по сценам. Сквозные ассеты (спрайты персонажей, UI) — в `common/`. Движку структура безразлична (имя образа берётся только из имени файла), но ручной работы с картинками будет много — структура нужна для людей. Следствие: имена файлов должны быть уникальны во всём `game/images/` независимо от папки.
- Теги и атрибуты — латиницей, в нижнем регистре, без слов `at`, `as`, `behind`, `onlayer`, `with`, `zorder`.
- Тег `bg` — только для переиспользуемых фонов, общих для разных сцен и глав (лежат в `common/`): `bg kitchen day.jpg`. Полноэкранные кадры конкретной сцены/части под `bg` не идут — они носят тег своей части (см. выше). Сложные/составные образы — оператором `image` в `images.rpy`.
- Ассеты из `shuffling_man_assets/Черновик` копируем в `game/images/` уже с правильными именами; `.psd` в игру не кладём.
- `scene` — смена сцены (очищает слой), `show`/`hide` — спрайты, переходы — `with dissolve` и т.п.
- Анимации и трансформации — через ATL, а не Python.
- **Координаты в позиционных свойствах (`pos`, `xpos`, `ypos`, `align`, `anchor` и т.п.) — типозависимы**: `int` — пиксели, `float` — доля экрана/контейнера (`0.5` — половина, `785.0` — 785 ширин экрана, объект улетает за кадр). Пиксельные координаты передавать только как `int`; результаты Python-вычислений (деление, интерполяция) приводить явно — `int(round(...))`. Симптом ошибки: изображение «не отображается» без каких-либо ошибок.

#### Визуальные эффекты

- Переиспользуемые эффекты камеры/экрана — `game/common/camera_fx.rpy` (зерно-помехи, наезды и дрожь камеры, тревожное покачивание). Перед добавлением туда нового эффекта — проверить `libs/7dots.rpy` (skill `7dots-reference`), чтобы не дублировать готовое.
- **Зерно-помехи — один экран `fx_noise_screen` на всю игру, от главного меню до конца, поверх всего.** Сила, включение и собственная постеризация зерна (`noise.steps`: 0 — плавное зерно, от 2 — ступени серого) — только в `fx_config.yaml` (FX Tuner). Сцены и мини-игры зерно не усиливают, не ослабляют и не показывают своё: второй `show fx_noise` дал бы двойной слой. При «Меньше движения» зерна нет.
- **Параллакс за мышью — один на всю игру** (`game/common/parallax.rpy`, по образцу проекта plenka). Слой `master` целиком едет за курсором через `config.layer_transforms`, снаружи `camera`: сцены параллакс не объявляют, их зумы и дрожь работают поверх. Слой `lockgame` и UI не двигаются. World-space кнопки на камере — `follow_camera()`, без камеры — `parallax_follow()`; ближний план (ГГ, руки у пианино) отделяется от фона трансформом `parallax_near`. Амплитуды и плавность — `parallax.*` в `fx_config.yaml` (FX Tuner), игрок выключает кнопкой «Параллакс» в настройках; при «Меньше движения», под автотестами и пока открыт Position Tuner параллакса нет.
- **Постеризация — глобальный эффект поверх камеры** (шейдер `sm.posterize` в `common/shaders.rpy`, подключение через `config.layer_transforms` в `common/camera_fx.rpy`). Формула исходного Unity-шейдера `floor(c·steps)/(steps−1)` с учётом premultiplied alpha. Охват `scene` — все слои мира без UI (слой, добавленный в init, подхватывается сам), `screen` — весь экран с UI. Вид эффекта задают `fx_config.yaml` и FX Tuner.
- Силой по сюжету управляет `default fx_posterize_strength` (0..1, множитель к силе из YAML): `$ fx_posterize_strength = 0.3` плавно ослабляет эффект; после момента вернуть к `FX_POSTERIZE_DEFAULT`. Точечно на один объект — `show x at posterize(4)`, снять — `show x at posterize_off`: обычный `at` наследует шейдер прошлого трансформа.
- **Пикселизация** — порт `Pixelate.shader` из nubick/unity-utils (MIT), шейдер `sm.pixelate`; устроена как постеризация: свой охват `scene`/`screen`, размер пикселя в точках экрана, сюжетная сила `default fx_pixelate_strength` (множитель к размеру ячейки). Эффекты одного охвата идут одним проходом слоя: сначала пикселизация, затем постеризация. Точечно — `show x at pixelate(8)`, снять — `pixelate_off`.
- **Ретушь** (шейдер `sm.grade`, группа `grade`): яркость, контраст и насыщенность всего кадра со своим охватом `scene`/`screen`, без сюжетной силы. В общем проходе слоя идёт между пикселизацией и постеризацией.
- **Хроматическая аберрация** (шейдер `sm.chroma`, группа `chroma`; по статье lettier «3D Game Shaders For Beginners»): каналы R/G/B разъезжаются от центра экрана, смещения — в F10. Сюжетная сила — `default fx_chroma_strength` (множитель к смещениям), удобно для резких моментов. С пикселизацией совместима: выборки снапятся к её сетке. Точечно — `show x at chroma()`.
- **Bloom** (шейдер `sm.bloom`, группа `bloom`): свечение ярких мест — порог с мягким коленом, размытие и добавка к кадру. Своя реализация в один проход по mipmap-копии слоя: шейдер Unity PostProcessing под Unity Companion License переносить нельзя. Кадры у нас без HDR, поэтому светится только то, что ярче порога в пределах 0..1.
- Новый параметр эффекта объявляется рядом с эффектом — `fx_param("группа.имя", default, lo, hi, doc="...")`, читается `fx_cfg("группа.имя")`. FX Tuner показывает его сразу, в YAML он попадает после сохранения (до этого действует `default`). Тип задаёт `default`: значение чужого типа в файле заменяется дефолтом, число вне диапазона прижимается к границе.
- **Вращаемым/масштабируемым спрайтам с позиционированием по `anchor`/`pos` — всегда `transform_anchor True`.** Активный `rotate` расширяет холст спрайта до квадрата со стороной-диагональю (`rotate_pad`), и без `transform_anchor` якорь отсчитывается от этого квадрата — объект уезжает с позиции. С `transform_anchor` якорь считается по самому спрайту и одновременно становится пивотом поворота/масштаба (примеры: стрелка метронома, ГГ за пианино в `chapter_1_scene_1.rpy`).
- **Состояние function-трансформов (сглаживание, дрожь, плавная альфа) — только в module-level `_fx_state` (`common/camera_fx.rpy`, через `_fx_step`) под уникальным ключом, и без сброса по `st ≈ 0`.** Атрибуты `trans.fx_*` теряются при пересборке обёртки (каждый `restart_interaction` на camera-слое и always_shown-экранах), а сброс по `st` даёт скачок эффекта при повторном применении трансформа (`camera at ...` на стыке сцен) — видимое «вздрагивание» камеры. Подробности — `.agents/rules/function-transform-state.md`.

#### Аудио

- Файлы — в `game/audio/`, ogg/opus предпочтительно. Имена в нижнем регистре, слова через `_`, без пробелов и дефисов.
- **Аудиосистема подключена**: `game/common/audio_manager.rpy`, по 5 каналов на линии `music` / `voice` / `sfx`. Контракт, примеры и ограничения — [docs/03_audio_system.md](docs/03_audio_system.md).
- Сценарии используют обёртки 7dots (`mplay`/`splay`/`sfxplay`/`vplay`), направленные в пул. Голые `play`/`stop`-операторы в сценариях не использовать.
- Затухания — `fadein`/`fadeout`; именованный слой — `tag`; наложение — `overlap`; громкость — `volume`.

#### Лейблы и поток управления

- Глобальные лейблы уникальны на весь проект и дублируют структуру повествования по той же схеме, что имена файлов: `chapter_1_scene_2`, `prologue_scene_1`, `ending_1`. Внутренние точки сцены — локальные лейблы `.loop`, `.after_choice`.
- `jump` — линейный переход, `call` — только когда нужен возврат; у каждого `call` в релизе должен быть `from`-клаус (авто-добавляется при сборке, опция «Add from clauses to calls»).
- Сцены связаны цепочкой `jump`: каждая сцена в конце прыгает на следующую, последняя делает `return` в главное меню. `call` — только для подпрограмм (мини-игры, вставки), не для перехода между сценами.
- Игровые циклы писать на языке Ren'Py (`while`, `menu`, `jump`), не в `python:` — иначе ломается сохранение посреди цикла.

#### GUI и стили

- Простая настройка — переменные `gui.*` в `gui.rpy`; экраны — в `screens.rpy`. Не переопределять экраны целиком без необходимости.
- Конфигурация (`config.*`) и стили меняются только в init-фазе, не по ходу игры.
- `config.name`, `config.version` — поддерживать актуальными в `options.rpy`.

#### Текст и перевод

- **Сценарный текст неприкосновенен**: не менять формулировки, порядок слов, орфографию и даже пунктуацию — ни в `docs/`, ни в репликах `.rpy`. Опечатки не исправлять самовольно — сообщать автору. Единственное исключение — техническое размещение нового или перемещение существующего текста: допустимо отредактировать строку в объёме, необходимом для размещения (например, добавить переносы), не более (правило — `.agents/rules/scenario_text_immutable.md`).
- Игра пишется на русском (язык None). Все строки интерфейса оборачивать в `_("...")`.
- В диалогах спецсимволы `{`, `[`, `%` экранируются удвоением (`{{`, `[[`, `%%`), кавычки — `\"`.
- Не редактировать уже написанные реплики без нужды после генерации `tl/` — ломаются идентификаторы переводов. Если правка неизбежна (опечатка), сохранять идентификатор через `id`-клаус: `e "Реплика." id start_61b861a2`.

#### Мультиязычность: как писать код, чтобы переводы добавлялись легко

Диалоги переводятся автоматически (генерация `translate`-блоков в `tl/<язык>/`), поэтому правила ниже касаются в основном интерфейса, кода и мини-игр.

- Любая литеральная строка, которую увидит игрок, — в `_("...")` в месте определения: тексты экранов, кнопки, имена персонажей (`Character(_("Марина"))`), пункты настроек, `renpy.notify`, подсказки мини-игр. `_()` помечает строку для перевода, перевод происходит при отображении.
- Строки собирать целиком, не склеивать из кусков: порядок слов в других языках другой. Вместо конкатенации — подстановки: `_("Найдено предметов: [count]")`. Переведённое значение в подстановке — через флаг `!t`: `"[mood!t]"`, где `mood` определён как `_("...")`.
- Одинаковые короткие строки с разным смыслом различать тегом контекста: `_("Начать{#menu}")`, `_("Начать{#minigame}")` — отображаются одинаково, переводятся раздельно.
- Логика не зависит от отображаемых строк: сравнивать ключи/константы (`if answer == "piano_key_3"`), не переведённый текст. В сейвы и `persistent` писать ключи, не строки — сохранённый текст не перепереведётся при смене языка.
- Мини-игры: весь видимый текст — через `text`/`textbutton` со строками в `_()`; никакого текста, «запечённого» в картинки. Если без текста в графике никак — класть переведённый вариант файла в `game/tl/<язык>/<тот же путь>`, движок подхватит его автоматически. Верстать экраны с запасом по ширине: перевод бывает в 1.5–2 раза длиннее оригинала; размеры кнопок не подгонять под длину русской строки.
- Служебные лейблы (внутренние циклы мини-игр, технические переходы) помечать `hide` (`label minigame_loop hide:`), чтобы не засорять файлы переводов.
- Шрифты: не хардкодить в экранах, использовать `gui.text_font` / стили — тогда для языка достаточно задать в `translate <язык> python` все три переменные `gui.text_font`, `gui.name_text_font`, `gui.interface_text_font` (`define gui.*` выполняются раньше `translate python`, поэтому ссылка `gui.name_text_font = gui.text_font` новое значение не подхватит) и `translate <язык> style`-блоки. Выбирать шрифты с покрытием кириллицы и латиницы.
- Python внутри `translate`-блоков — без побочных эффектов: при смене языка блок исполняется заново.
- Русские UI-строки поверх встроенных английских строк движка — через `translate None strings:` (файл `game/tl/None/common.rpym` уже отвечает за системные строки).
- Генерация переводов из CLI: `renpy-8.5.3-sdk\renpy.exe shuffling_man translate english`, выгрузка для переводчиков: `... dialogue english --strings`. Переключение языка в игре — action `Language("english")` / `Language(None)` на экране настроек. Проверка — Shift+D → «Show Translation Info».

#### Проверка и запуск

- На Windows перед коммитом из корня `shuffling_man_project` запускать `powershell -ExecutionPolicy Bypass -File .\shuffling_man\tools\check_project.ps1`. Скрипт делает полную Python-компиляцию, строгий lint (предупреждения дают ненулевой код возврата) и smoke-тесты замков.
- Эквивалентная команда lint вручную: `renpy-8.5.3-sdk\lib\py3-windows-x86_64\python.exe renpy-8.5.3-sdk\renpy.py shuffling_man lint --error-code --reserved-parameters --check-unclosed-tags --all-problems`. Консольный Python SDK устойчивее GUI-обёртки `renpy.exe` в CI и перенаправленном выводе.
- На Linux/macOS выполнить последовательно `renpy-8.5.3-sdk/renpy.sh shuffling_man compile --compile-python`, затем `renpy-8.5.3-sdk/renpy.sh shuffling_man lint --error-code --reserved-parameters --check-unclosed-tags --all-problems` и `renpy-8.5.3-sdk/renpy.sh shuffling_man test global`.
- Линт проверяет операторы Ren'Py, но не их Python-эквиваленты — предпочитать операторы (`show`, `play`) функциям (`renpy.show()`).
- Запуск из CLI: `renpy-8.5.3-sdk\renpy.exe shuffling_man run`.
- Коммиты — осмысленные, по одной сцене/фиче; в репозиторий не коммитим сейвы, кэш, `persistent`.
